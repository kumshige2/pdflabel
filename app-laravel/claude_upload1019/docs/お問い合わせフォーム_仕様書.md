# お問い合わせフォーム 仕様書

## 1. 概要

既存のLaravelアプリ（`adminlte2q_73`）に追加した「お問い合わせフォーム」機能。社内向け（ログイン済み社員が使う）の機能で、エンドユーザーが入力する「お問い合わせフォーム」と、管理者が確認・管理する「管理ページ」の2つで構成される。

## 2. 技術スタック

| 項目 | 技術 |
|---|---|
| フレームワーク | Laravel 10 |
| 言語 | PHP 8.1/8.2 |
| データベース | PostgreSQL（`pgsql_test`接続、`snno3_test`データベース） |
| 画面 | AdminLTE（`jeroennoten/laravel-adminlte`） |
| 認証 | 既存アプリの`auth`ミドルウェア + `role_id`ベースのGate（`AuthServiceProvider`） |

## 3. データベース設計

### `contacts` テーブル

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| id | bigint | PK, AUTO_INCREMENT | 自動採番 |
| name | string(255) | NOT NULL | 名前 |
| email | string(255) | NOT NULL | メールアドレス |
| subject | string(255) | NOT NULL | 件名 |
| body | text | NOT NULL | 本文 |
| status | string(255) | NOT NULL, DEFAULT '新規' | ステータス |
| created_at | timestamp | NULLABLE | 作成日時 |
| updated_at | timestamp | NULLABLE | 更新日時 |

モデル: `app/Models/Contact.php`（`$fillable = ['name','email','subject','body','status']`。`$table`指定やカスタム主キー設定は不要な、Laravel標準の単純なモデル）

### ステータスの種類

| 値 | 説明 |
|---|---|
| 新規 | 初期状態（デフォルト値） |
| 対応中 | 対応を開始した状態 |
| 解決済み | 対応が完了した状態 |

## 4. ルーティング

`routes/web.php`に、既存の`auth`ミドルウェアグループ内へ追記する形で実装。

### お問い合わせフォーム（公開側）

| メソッド | URL | ルート名 | 処理内容 |
|---|---|---|---|
| GET | `/contact` | contact.create | 入力フォーム表示 |
| POST | `/contact/confirm` | contact.confirm | 確認画面表示 |
| POST | `/contact` | contact.store | 送信処理（保存 or 「戻る」分岐） |
| GET | `/contact/complete` | contact.complete | 完了画面表示 |

### 管理ページ

| メソッド | URL | ルート名 | 処理内容 |
|---|---|---|---|
| GET | `/admin/contacts` | admin.contacts.index | 一覧表示 |
| GET | `/admin/contacts/{contact}` | admin.contacts.show | 詳細表示 |
| PATCH | `/admin/contacts/{contact}/status` | admin.contacts.updateStatus | ステータス更新 |

※ いずれも`auth`ミドルウェアが必須。Gate（`@can`）による制御はサイドバーメニューの表示/非表示のみで、URLを直接知っていればアクセス自体は可能（既存アプリの他機能と同じ方式）。

## 5. お問い合わせフォーム機能

### 5.1 画面遷移フロー

```
入力フォーム(GET /contact) → 確認画面(POST /contact/confirm) → 送信処理(POST /contact) → 完了画面(GET /contact/complete)
                                  ↓ 「戻る」
                              入力フォーム（入力値復元）
```

### 5.2 入力フォーム（`contact/create.blade.php`）

| 項目 | 入力形式 | 必須 |
|---|---|---|
| 名前 | テキスト | はい |
| メールアドレス | メール | はい |
| 件名 | テキスト | はい |
| 本文 | テキストエリア | はい |

- バリデーションエラー時・「戻る」での遷移時は`old()`により入力値が復元される
- 例外発生時のエラーメッセージ表示として `@if ($errors->any())` ブロックを上部に設置（実機検証で、例外時にエラーが画面に出ない不具合が見つかり追加したもの）

### 5.3 バリデーションルール（`app/Http/Requests/StoreContact.php`）

| フィールド | ルール |
|---|---|
| name | required, string, max:255 |
| email | required, email, max:255 |
| subject | required, string, max:255 |
| body | required, string |

### 5.4 確認画面（`contact/confirm.blade.php`）

- バリデーション通過後の入力値を、**hidden fieldに埋め込んで再送信する方式**（セッションは使わない。既存の`T_sei_sanq01Controller`の作法に合わせた）
- 表示項目: 名前、メールアドレス、件名、本文
- 操作ボタン（同じフォームを`name="action"`の値で分岐）:
  - **送信する**（`value="submit"`）: 保存処理へ
  - **戻る**（`value="back"`）: 入力フォームへ（hidden fieldの値を`withInput()`で復元）

### 5.5 送信処理（`ContactController::store()`）

- `$request->action === 'back'` の場合: 入力フォームへリダイレクト（入力値保持）
- それ以外: `Contact::create($request->validated())` で保存 → 完了画面へリダイレクト
- 保存時に例外が発生した場合: 入力フォームへリダイレクトし、`withErrors()`でエラーメッセージを渡す（5.2の`@if ($errors->any())`で表示）

### 5.6 完了画面（`contact/complete.blade.php`）

- 「お問い合わせありがとうございました。」を表示
- 「戻る」ボタンで入力フォームへ

## 6. 管理ページ機能

### 6.1 一覧表示（`Admin\ContactController::index()` / `admin/contacts/index.blade.php`）

- `Contact::latest()->paginate(20)` で新しい順・20件ずつページネーション表示
- 表示カラム: ID、名前、件名、ステータス、受付日時
- IDをクリックすると詳細画面に遷移
- ステータスはバッジで色分け: 新規=`badge-danger`（赤）、対応中=`badge-warning`（黄）、解決済み=`badge-success`（緑）

### 6.2 詳細表示（`Admin\ContactController::show()` / `admin/contacts/show.blade.php`）

- 表示項目: 名前、メールアドレス、件名、本文、受付日時
- ステータス変更用ドロップダウン（新規 / 対応中 / 解決済み）＋「更新する」ボタン
- 更新成功時、flashmessageで「ステータスを更新しました」を表示（既存アプリのflashmessageモーダル表示パターンを使用）

### 6.3 ステータス更新（`Admin\ContactController::updateStatus()`）

- バリデーション（`app/Http/Requests/UpdateContactStatus.php`）: `status`が`新規`/`対応中`/`解決済み`のいずれかであること
- 更新後、詳細画面にリダイレクト（成功メッセージ付き）

## 8. 権限・メニュー表示

- `config/adminlte.php`の`'menu'`配列に以下を追加することで、サイドバーに表示される。

```php
[
    'text' => 'お問い合わせ一覧',
    'url'  => 'admin/contacts',
    'icon' => 'fas fa-fw fa-envelope',
    'can'  => ['system', 'admin', 'user'],
],
```

- `AuthServiceProvider`の`Gate::define()`は`role_id`の**完全一致**で判定される（例: `'user'`ゲートは`role_id==9`の時だけ通る。「9以上」ではない）。複数の権限層に見せたい場合は`'can'`に配列で複数指定する。

## 9. セキュリティ対策

| 対策 | 実装方法 |
|---|---|
| CSRF保護 | 全フォームに`@csrf`（または`{{ csrf_field() }}`） |
| XSS防止 | Bladeの`{{ }}`による自動エスケープ（本文の改行は`white-space: pre-wrap`のCSSで表示し、`{!! !!}`は使用していない） |
| 認証 | `auth`ミドルウェアで未ログインアクセスを拒否 |
| マスアサインメント防止 | `Contact`モデルの`$fillable`で許可カラムを明示 |

## 10. 実装時の注意点・教訓（今後の参考用）

- Blade側の`@can('system')...<li><a>...@endcan`ブロックは、`@extends`する子テンプレートの`@section`の外に書くと**実際には画面に出力されない**。実際に動くサイドバーメニューは`config/adminlte.php`の`'menu'`配列で管理されている
- HTMLフォームは`PUT`/`PATCH`/`DELETE`を直接送信できないため、`@method('PATCH')`で隠しフィールド（`_method`）を使ったメソッド偽装を行っている
- ビューのフォルダ名は**単数形/複数形を間違えやすい**（`contact/`と`admin/contacts/`）。配置ミスは`View [xxx] not found`エラーで気づける
- devcontainerでの動作確認は、実際のBreezeログイン画面が無い環境のため、PHPUnitの`actingAs()`でログイン済み状態を再現してテストした

## 11. 既知の課題（申し送り事項）

- `database/factories/UserFactory.php`が`email_verified_at`カラムを設定しているが、実際の`users`テーブル（`2023_04_10_114314_create_users_table.php`）にこのカラムが存在しない。`User::factory()->create()`を呼ぶと失敗する（本機能とは無関係の、既存コードベース側の不具合）
- 管理一覧・詳細ページは、ルート自体には権限制御のミドルウェアが掛かっておらず、URLを直接知っていれば`auth`ログインユーザーなら誰でもアクセス可能（メニュー非表示だけで防いでいる。既存アプリの他機能と同じ方式を踏襲）
